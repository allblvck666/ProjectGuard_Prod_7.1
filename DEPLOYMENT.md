# ProjectGuard: выпуск и быстрый откат

## Зафиксированная версия

- Основной репозиторий: `allblvck666/ProjectGuard_Prod_7.1` (backend и действующий frontend).
- GitHub `main` на 08.09.2026: `39c035cb172c90228679fcb737bcc19272570029`.
- Ветка отката в GitHub: `rollback/production-2026-09-08`.
- Работающий frontend подтверждает `build-commit=39c035c`; дата сборки 21.08.2026.
- Render подтвердил ту же текущую версию backend; точные deploy ID и прежние настройки обоих сервисов записаны в частном журнале выпуска.
- Старый отдельный репозиторий frontend не является источником августовского интерфейса.

## Условия выпуска

1. В Render записать текущие deploy ID обоих сервисов и их настройки сборки, ветку, commit, а также прежний Health Check Path backend, включая пустое значение, если проверка по HTTP не настроена. Убедиться, что сохраняется подключение к той же PostgreSQL, BOT_TOKEN и JWT_SECRET/SECRET_KEY. Секреты не помещать в GitHub, документацию и чат. На существующем backend установить Health Check Path `/api/ready` для нового выпуска: он отвечает успешно только после подготовки базы и настройки webhook. Не создавать новые сервисы через Blueprint вместо уже работающих.
2. В Recovery базы `projectguard-db` создать свежий logical export и скачать его в закрытое хранилище. Проверить чтение оглавления `pg_restore --list` и восстановление в отдельную тестовую БД совместимой версии. Не восстанавливать поверх рабочей базы.
3. Из окружения сервиса запустить `python scripts/access_preflight.py`. Сохранить частный отчёт. Если есть активные пользователи без подтверждаемого Telegram ID или несколько записей с одним нормализованным ID, сначала согласовать привязку существующих аккаунтов. Не создавать им заменяющие аккаунты и не сбрасывать роли.
4. Проверить тесты backend на SQLite и PostgreSQL, сборку frontend и сценарии входа, редактирования, конфликтов, восстановления, продления и истории. Тесты используют вымышленные данные и не запускают боевого Telegram-бота.
5. Приостановить автоматическую выкладку обоих сервисов. Сначала вручную выпустить backend: августовский frontend уже передаёт подписанный Telegram initData и JWT, а старый backend не умеет сохранять новые поля и сбрасывает роли при входе. Сразу после проверки backend выпустить frontend того же коммита и проверить вход через настоящий Telegram. В коротком промежутке старый интерфейс может отклонить редактирование без версии записи и старый способ выгрузки; новая форма не должна попасть к старому серверу, который молча проигнорирует часть полей.
6. Повторить read-only preflight. Отпечаток доступа должен совпасть при отсутствии самостоятельных администраторских изменений; новые пользователи рассматриваются отдельно. Существующие id, роли, блокировки и привязки сохраняются.
7. После успешного входа через настоящий Telegram и проверки восстановления истёкшего сеанса завершить переход через опциональный `AUTH_LEGACY_TOKENS_UNTIL`, оставив `AUTH_MIN_TOKEN_VERSION=0`. Выбрать UTC-срок не раньше чем через 30 дней после прекращения выдачи токенов старым backend, включая завершение старых процессов. До этого срока действующие старые сеансы сохраняются; начиная с него требуются токены версии не ниже 1. Для выпуска 08.09.2026 выбран `AUTH_LEGACY_TOKENS_UNTIL=2026-10-08T16:05:00Z`: это 30 дней плюс 6 минут 28 секунд после готовности первого нового backend в `15:58:32Z`, с запасом на завершение старых процессов. Перед применением сверить остановку последнего legacy issuer и отсутствие последующих откатов к нему по частному журналу выпуска. Если старый backend работал позже, в том числе при откате, отсчитать 30 дней заново от последней такой выдачи. Не включать немедленный `AUTH_MIN_TOKEN_VERSION=1` только ради окончания выпуска: он отзывает ещё действующие старые сеансы, в том числе в давно открытом frontend.

## Откат приложения

При ошибках доступа или основных действий в Render → Deploys выбрать записанный предыдущий успешный deploy backend и выполнить Rollback, затем вернуть frontend. Штатный Rollback повторно использует артефакт и Health Check Path выбранного старого выпуска; проверить это значение после отката. Текущие настройки сервиса при этом не переписываются. Если вместо Rollback потребуется заново собирать августовский commit, сначала вернуть записанный прежний Health Check Path (включая пустое значение): `/api/ready` в августовском коде отсутствует. Не подставлять `/` без проверки. Проверить статус Live/Deployed, августовский build-commit, вход существующего пользователя и чтение защит.

Откат кода использует ту же базу: новые записи и история должны сохраниться. Изменения схемы в этом выпуске должны быть совместимы с августовским кодом; удаление таблиц, переименование полей и массовое изменение ролей запрещены. Не восстанавливать старый снимок базы ради отката кода: это потеряет новые действия пользователей. Резервную копию базы применять только при подтверждённом повреждении данных после отдельной проверки.

Если предыдущий deploy недоступен в интерфейсе, собрать оба сервиса из `rollback/production-2026-09-08` или указанного полного SHA. Сначала сверить настройки сборки и подключения.

## Совместимость сеансов

Секрет JWT сохраняется. По умолчанию (`AUTH_MIN_TOKEN_VERSION=0`, `AUTH_LEGACY_TOKENS_UNTIL` не задан) существующие действительные сеансы совместимы с первым этапом выпуска. Новые входы проверяют подпись Telegram и используют роль из существующей записи; новые токены имеют `auth_version=1`. Пользователей и их роли не удалять.

В августовском commit `39c035c` проверены все три места выдачи JWT: `create_access_token` и `create_jwt` в `backend/auth.py` задают 30 дней, старый Telegram-вход в `backend/users.py` — 7 дней. Максимальный срок законного старого токена — 30 дней. Поэтому срок завершения перехода через 30 дней после окончательной остановки старых issuer не сокращает обычную жизнь этих сеансов. Настройка не продлевает `exp` ни одного токена.

`AUTH_LEGACY_TOKENS_UNTIL` принимает ISO timestamp с явным UTC (`Z` или `+00:00`). Отсутствие настройки сохраняет прежнее поведение; неверный формат или другая временная зона останавливают запуск с ошибкой конфигурации. До указанного момента действует `AUTH_MIN_TOKEN_VERSION`; в сам момент и после него минимум равен `max(AUTH_MIN_TOKEN_VERSION, 1)`. Поэтому версия 1 продолжает работать, а более строгий явный минимум никогда не понижается сроком. Для возврата к приёму старого формата потребуется одновременно убрать срок и вернуть минимум 0; это повторно открывает остаточный риск и не является обычным шагом успешного выпуска.

Ранее выданные поддельные JWT нельзя отличить от настоящих старых токенов без отзыва прежнего формата. До срока этот остаточный риск сохраняется. После него старый формат вызывает HTTP 401 и текущий frontend выполняет подтверждённый повторный вход, сохраняя id, роль и привязки аккаунта. Пользователю с давно открытым приложением и устаревшими данными Telegram может понадобиться закрыть и снова открыть Mini App. Немедленный `AUTH_MIN_TOKEN_VERSION=1` остаётся отдельным вариантом отзыва, когда он осознанно требуется; он не нужен для плавного перехода с заданным сроком.
