# ProjectGuard: выпуск и быстрый откат

## Зафиксированная версия

- Основной репозиторий: `allblvck666/ProjectGuard_Prod_7.1` (backend и действующий frontend).
- GitHub `main` на 08.09.2026: `39c035cb172c90228679fcb737bcc19272570029`.
- Ветка отката в GitHub: `rollback/production-2026-09-08`.
- Работающий frontend подтверждает `build-commit=39c035c`; дата сборки 21.08.2026.
- Точную текущую версию backend необходимо сверить в Render Events до выпуска.
- Старый отдельный репозиторий frontend не является источником августовского интерфейса.

## Условия выпуска

1. В Render записать текущие deploy ID обоих сервисов и их настройки сборки, ветку, commit, а также прежний Health Check Path backend, включая пустое значение, если проверка по HTTP не настроена. Убедиться, что сохраняется подключение к той же PostgreSQL, BOT_TOKEN и JWT_SECRET/SECRET_KEY. Секреты не помещать в GitHub, документацию и чат. На существующем backend установить Health Check Path `/api/ready` для нового выпуска: он отвечает успешно только после подготовки базы и настройки webhook. Не создавать новые сервисы через Blueprint вместо уже работающих.
2. В Recovery базы `projectguard-db` создать свежий logical export и скачать его в закрытое хранилище. Проверить чтение оглавления `pg_restore --list` и восстановление в отдельную тестовую БД совместимой версии. Не восстанавливать поверх рабочей базы.
3. Из окружения сервиса запустить `python scripts/access_preflight.py`. Сохранить частный отчёт. Если есть активные пользователи без подтверждаемого Telegram ID или несколько записей с одним нормализованным ID, сначала согласовать привязку существующих аккаунтов. Не создавать им заменяющие аккаунты и не сбрасывать роли.
4. Проверить тесты backend на SQLite и PostgreSQL, сборку frontend и сценарии входа, редактирования, конфликтов, восстановления, продления и истории. Тесты используют вымышленные данные и не запускают боевого Telegram-бота.
5. Приостановить автоматическую выкладку обоих сервисов. Сначала вручную выпустить backend: августовский frontend уже передаёт подписанный Telegram initData и JWT, а старый backend не умеет сохранять новые поля и сбрасывает роли при входе. Сразу после проверки backend выпустить frontend того же коммита и проверить вход через настоящий Telegram. В коротком промежутке старый интерфейс может отклонить редактирование без версии записи и старый способ выгрузки; новая форма не должна попасть к старому серверу, который молча проигнорирует часть полей.
6. Повторить read-only preflight. Отпечаток доступа должен совпасть при отсутствии самостоятельных администраторских изменений; новые пользователи рассматриваются отдельно. Существующие id, роли, блокировки и привязки сохраняются.
7. После успешного входа через настоящий Telegram и проверки восстановления истёкшего сеанса включить `AUTH_MIN_TOKEN_VERSION=1` на backend. Сначала убедиться, что все активные пользователи имеют проверенные привязки и получили новый frontend. Старый JWT тогда вызывает прозрачное подтверждение Telegram и заменяется новым, без создания пользователя или изменения роли. Пользователю с давно открытым приложением и устаревшими данными Telegram может понадобиться закрыть и снова открыть Mini App. Не включать флаг до этих проверок.

## Откат приложения

При ошибках доступа или основных действий сначала вернуть backend его записанный прежний Health Check Path, затем в Render → Events выбрать записанный предыдущий успешный deploy и выполнить Rollback. Путь `/api/ready` отсутствует в августовском коде: если оставить его в настройках сервиса, старая версия будет отвечать 404 на проверку готовности и быстрый откат может не завершиться. Вернуть именно записанное прежнее значение, в том числе пустое; не подставлять `/` без проверки. После backend вернуть frontend на записанный предыдущий deploy. Проверить статус Live/Deployed, августовский build-commit, вход существующего пользователя и чтение защит.

Откат кода использует ту же базу: новые записи и история должны сохраниться. Изменения схемы в этом выпуске должны быть совместимы с августовским кодом; удаление таблиц, переименование полей и массовое изменение ролей запрещены. Не восстанавливать старый снимок базы ради отката кода: это потеряет новые действия пользователей. Резервную копию базы применять только при подтверждённом повреждении данных после отдельной проверки.

Если предыдущий deploy недоступен в интерфейсе, собрать оба сервиса из `rollback/production-2026-09-08` или указанного полного SHA. Сначала сверить настройки сборки и подключения.

## Совместимость сеансов

Секрет JWT сохраняется. По умолчанию (`AUTH_MIN_TOKEN_VERSION=0`) существующие действительные сеансы совместимы с первым этапом выпуска. Новые входы проверяют подпись Telegram и используют роль из существующей записи; новые токены имеют версию подтверждённой авторизации. Ранее выданные поддельные токены нельзя отличить от настоящих старых токенов без отзыва прежнего формата. До включения `AUTH_MIN_TOKEN_VERSION=1` этот остаточный риск сохраняется. Флаг включается только на завершающем этапе после проверки прозрачного повторного входа; пользователей и их роли не удалять.
